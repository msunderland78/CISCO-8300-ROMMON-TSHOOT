Static receiver analysis indicated a 0x200000 (2 MiB) input limit. It expects LZMA
FORMAT_ALONE with a real uncompressed-size header; unknown-size FF header
was unsuitable. It checks the first 64 KiB CRC (0xDEAB7E4E for FF-filled
prefix), skips that prefix and programs linearly from flash offset 0x10000
in 128 KiB chunks. No supported offset or sparse update mode was found.
Consequently, sending a tiny loader or an arbitrarily sparse/truncated image
is NOT a validated way to update just 0xA60000. These format/write-path
conclusions came from static analysis; no accepted recovery transfer validated
the whole decode/program sequence on this device.

Compression trials included lc/lp/pb combinations, 16 MiB dictionary, deeper
match search, alternate padding/truncation trials and official LZMA SDK 26.05:
  initial hybrid .bin.lzma: 2,186,318 bytes

    lc=1, lp=2, pb=2, dict=16777216, nice_len=273, depth=256
  best SDK result: 2,176,859 bytes (79,707 bytes too large)
Decompression of final candidates reproduced the hybrid hash exactly.
